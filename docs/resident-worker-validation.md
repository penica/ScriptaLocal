# Resident worker and HTTP validation

The worker entry point is `python -m scriptalocal.resident_worker --config /state/worker.json`. It loads Kraken and TrOCR once, derives the complete pipeline configuration, and repeatedly executes leased stages. One explicitly assigned CUDA device is required. Both offline environment flags must be set. It does not migrate the database or download models at startup. Library environments remain separate: the API uses the 24-package CPU lock and the worker uses the 171-package GPU lock.

Required absolute-path configuration keys are `dsn_file`, `artifacts_root`, `originals_root`, `model_root` and `status_root`. Also required are `recognition_manifest_sha256`, `runtime_image` (an immutable image ID) and `worker_id`. Optional keys are `precision`, `queue`, `poll_seconds`, `ready_interval_seconds`, `torch_threads`, `license` and `scripts`. Defaults retain the verified Bern MIT Kurrent profile, FP32 and two native threads. GPU access is assigned by Docker, not a request field.

API and worker must share original/artifact roots. The status root is mounted at the same absolute path in both containers. The worker publishes `profiles.json` there with the actual pipeline manifest and a `ready.json` marker. Configure the API's `profiles_file` to that generated registry. This runner owns a single registry/profile; multiple workers must not overwrite the same registry. Multi-worker inventory/topology acceptance remains HTR-023 work.

An exclusive filesystem lock prevents competing publishers from replacing a live readiness marker. Refresh is atomic and periodic; the API rejects stale, future-dated or mismatched configurations. A refresh failure stops further claims. Clean shutdown removes the marker. Abrupt death leaves an expiring marker, so readiness is not an immediate process-death detector. Queue heartbeat/lease fencing remains authoritative for stage ownership. SIGTERM drains the current stage before stopping; a supervisor's forced termination relies on lease recovery instead.

Five component tests pass for marker refresh, exclusive ownership, publication failure, registry/configuration/expiry checks and invalid intervals. They do not demonstrate arbitrary filesystem-hang recovery or an overall job deadline.

On 12 November 2026, two sequential real HTTP uploads of the supplied manuscript row completed in 66.959 and 65.889 seconds after readiness. Each returned 18 cells and 24 lines; cells and provenance were identical and original bytes were unchanged. A duplicate upload with the same idempotency key returned the same job. One worker-ready event and six completed-stage events establish one recognizer load across these two jobs. All cells require review. These are two runs of one row, not a quality corpus, p50/p95 benchmark or Registers application round trip.

The validation API bound only `127.0.0.1:8092`, using a dedicated frontend bridge plus the internal database network. The worker had only the internal database network and GPU 0; the database had no host port. Containers ran as UID 1000 with read-only root filesystems, dropped capabilities, no-new-privileges and explicit CPU/RAM/PID limits. Source code was mounted read-only over immutable validation image IDs; a production image rebuild/deployment is still required.

Private receipts, raw JSON and reports are under `data/validation/ocr-http-bootstrap/`; raw manuscript readings remain outside Git. The separate interrupted-worker probe killed the worker with SIGKILL while segmentation was running, then restarted the same container. The same job completed in 89.471 seconds including interruption/reload: layout and recognition each committed on attempt 1, segmentation on attempt 2, with exactly one result artifact and revision 1. Cells and provenance matched the uninterrupted runs. All three HTTP result bodies passed JobResult validation. Clean worker shutdown removed readiness; the API reported the model unavailable. Restarting the API preserved all three successful jobs/results, and source bytes remained unchanged. Both temporary validation containers are now stopped. See `docs/validation/resident-http.json`.
