# Correction revisions

`POST /v1/jobs/{job_id}/revisions` accepts a bounded JSON `RevisionInput`. A completed current revision is required. `expected_revision` must match; a stale save returns 409. Foreign or missing jobs return 404, and write capability is required. Actor identity comes from the authenticated server-side caller principal, and submission time comes from PostgreSQL; clients cannot submit either field. A service token identifies that service principal, not an independently verified human person.

The admission transaction locks the job, validates the immutable base result and targets, checks active-job capacity, and inserts a new revision and append-only edit record. It queues work and advances the current revision together. Concurrent writers cannot silently overwrite one another. Raw machine text/state, original result bytes and earlier corrections remain in their prior revision artifacts.

Text-only changes queue recognition-stage result assembly. The pipeline reads the base result and server-attributed edit record, changes effective readings, recomputes cell text with exact LF/null semantics, and publishes a new result without invoking segmentation or recognition. Existing model/geometry warnings remain. Human-review warnings created by a prior unreadable edit can be removed when a later saved reading resolves that state. Original inference timings remain in `stage_seconds`; `correction_assembly` measures the latest assembly pass.

Divider changes validate encoded-image bounds, orientation, crossings and the minimum cell width from the pinned layout configuration. They queue layout, segmentation and recognition again. Old line corrections are not attached to regenerated lines, even if a deterministic line ID happens to repeat. Prior results remain retrievable with `GET /v1/jobs/{job_id}/result?revision=N`. Without that parameter, result retrieval requires the current revision to have succeeded. Cancelling a pending revision never changes a completed earlier result.

The API shares bounded streaming/concurrency controls with image uploads. `maximum_revision_bytes` defaults to 2 MiB and is configurable; upload timeouts and credential reauthentication also apply. Geometry and line-ID corrections cannot be submitted together. Synthetic validation text is not reference transcription and must not enter training ground truth.

On 12 November 2026, all 30 API, 16 synthetic pipeline, 21 queue, 16 worker and 65 core tests passed after migration 003. Coverage includes attribution, stale saves, conflicting writers, unknown/foreign targets, body limits, null/unreadable readings, resolved human warnings, immutable raw history, cancellation and geometry regeneration. The pipeline tests check model call counters to establish that text revisions do not invoke either model. The real HTTP/GPU probe also passed: initial recognition returned 18 cells/24 lines, a synthetic text revision completed in 0.617 seconds, and geometry regeneration completed in 62.948 seconds with 18 cells. The database contained seven successful stages (3 + 1 + 3), two edit records and exactly one result artifact per revision. Historical result bytes remained identical after both edits and an isolated PostgreSQL restart. Source fingerprints match the tested checkout. Temporary API/worker services are stopped. See `docs/validation/revisions.json`.

Production deployment must keep a matching pipeline configuration available for queued revisions. This prototype does not migrate an old job silently onto changed model/code settings. Backup/restore acceptance must include `sl_revision_edits`, historical result artifacts and their referenced source files.
